## 视觉与尺寸

采用竖版数据海报，保留实体高级纸品的材质感，减少文字表达。

| 项目 | 设计值 |
| --- | --- |
| 默认画幅 | 1080 × 1440 px，3:4 |
| 可选画幅 | 1080 × 1080 px，1:1，单独重排而非裁切 |
| 导出格式 | PNG；产品实现时固定颜色表现，不随系统深浅主题改变导出 |
| 安全边距 | 四周 72 px |
| 主数字 | 约 160–184 px；长数字与方图适当缩小 |
| 辅助文字 | 约 40 px，需检查手机缩略图可读性 |

画面层级：顶部昵称、生成月份和等级；中间个人纹样；纹样下方累计 I 量与原生 Token 对照；底部活跃日、主要工具、来源范围和观测时间范围。

所有等级使用完整的版式和纹样。升级体现在颜色、反光、边缘与工艺层次；低等级不使用灰掉、锁定或未完成的视觉。数字图片模拟纸张、压凹、珠光、拉丝及烫箔的视觉效果，不宣称具备实体触感。

不在首版分享图堆放长文案、输入/输出/缓存明细、升级进度条或未经证实的百分位。详细统计继续留在报告中。传播二维码已接入 v0.1，原概念预览保留为对照。

## 字段约定

- 主数字明确标为“累计 I 量”，与累计等级保持同一范围。
- 展示提案：1 I = 1,000,000 原生 Token，仅作数量缩写，不是智力、效率或能力分数。
- Token 对照保留在数字下方，产品中可进一步查看精确整数及计数口径。
- 来源范围保留“本地记录 · 含缓存”等简短标识；用户昵称可选。
- 最多展示两个主要工具，按累计 Token 降序排序；更多工具显示“+N”。过长昵称与工具文本适当缩小并省略，防止侵入其他信息区。
- 活跃天数只按有有效记录的日期计算。缺失数据不补零。
- 生成月份与实际观测日期分别显示，避免把历史累计误解为当月用量。
- 产品纹样用有记录日的用量取对数并归一化，轻微改变固定数量曲线的控制点；没有读取对话内容。纹样是抽象表达，不是可反查精确数值的统计图。不同等级不靠增加纹样数量来表示人的价值。

## 等级规则提案

设 T 为去重后的累计有效原生 Token 整数。按统计内核既有口径计算输入加输出，缓存与推理均作为子集，不重复相加。账号摘要与本地明细保持独立。

| 等级 | Token 区间 | I 区间 | 视觉 |
| --- | --- | --- | --- |
| L1 素棉 | 0 < T < 10,000,000 | 0 < I < 10 | 暖白、细纸纹、压凹 |
| L2 染纸 | 10,000,000 ≤ T < 100,000,000 | 10 ≤ I < 100 | 灰绿、染纸、浅浮雕 |
| L3 珠光 | 100,000,000 ≤ T < 1,000,000,000 | 100 ≤ I < 1,000 | 深蓝、珠光、局部银光 |
| L4 钛银 | 1,000,000,000 ≤ T < 10,000,000,000 | 1,000 ≤ I < 10,000 | 冷银、拉丝、金属边缘 |
| L5 墨金 | T ≥ 10,000,000,000 | I ≥ 10,000 | 墨绿黑、局部烫金、金色切边 |

- 升级点按约十倍量级递增，作为用量跨度较大的编程工具场景的初始设计。后续用真实样本评估升级速度，不能把这些门槛当成百分位。
- 等级不按月清零。重复导入不升级，统计纠错后重新计算。
- 已确认零用量或无有效记录时不授予 L1；未接入与零用量必须区分，界面显示对应的“待记录”或“未接入”。
- 等级判断使用原始整数，不使用取整后的 I 显示值。小于 0.01 I 的正数显示“<0.01 I”，不能显示成零。
- 跨扫描累计已由 SQLite 历史库实现；清理原日志不删除已保存记录。仍需用户备份历史库或 JSONL，不能恢复首次扫描前已删除的日志。
- 本地记录可修改。当前等级不是服务商认证，也不代表费用、算力等价或产出质量。

## 传播二维码：基线与 v0.1 实现

用户明确要求保留并推进传播二维码。它帮助看到分享图的人进入 TokenMe，生成自己的分享图。

设计起点：

- 在两种画幅底部预留独立区域，二维码与品牌署名共同排版，避免覆盖主数字、纹样和必要的来源范围。
- 暂以 160–192 px 的整体二维码区域试排；最终尺寸随编码内容、模块数及缩略图扫码结果确定，不能只靠视觉选定。
- 使用清晰实色底和高对比模块，保留标准要求的静区；不把金属纹理、渐变、透明度或文字叠在码上。
- 搭配极短入口文案，例如“生成我的”，允许用户关闭传播元素。
- v0.1 链接到公开项目入口 `https://github.com/lmf112358/TokenMe`，提供安装与使用说明。独立落地页和品牌域名留待后续。
- 默认不编码昵称、用量、账号标识、原始记录或个人档案。若以后需要公开个人档案，另行设计明确的发布选择。
- 入口链路：看到图片 → 扫码 → 理解产品 → 生成自己的分享图。百分位展示仍需真实、同口径比较样本。

后续验收：两种画幅原图可扫码；经常见分享压缩后仍可识别；另一台手机可正确打开目标页面；关闭二维码后布局仍完整。扫码能力需实际验证，不以二维码已绘制代替成功。

## 已做与待做的验证

已做：首版竖图与方图视觉检查；360 px 窄屏检查；L1/L5 切换及大数字排版；确认生成的 PNG 像素分别为 1080 × 1440 与 1080 × 1080。

产品接入验证：18 项 Python 测试和 6 项 Node.js 规则测试；真实累计报告、月份切换后的累计隔离、长昵称、手机窄屏、两种画幅与 PNG 文件生成。预览和导出共用同一画布，点击保存时冻结像素与尺寸。

v0.1 补齐：SQLite 累计与事务更新、备份恢复；两个画幅的可关闭二维码。码区 164 × 164 px，33 × 33 模块，每模块 4 px，四模块白色静区；CTA 为“生成我的”。竖图与方图底部各自重排，扫码区域不叠加纹理。

实际导出图片经 ZXing 解码，原尺寸及缩至 720 / 540 px 宽、JPEG 85 质量均返回公开仓库 URL。该检查不是对所有社交平台压缩和手机相机的兼容保证。

待做：更多字体与浏览器、真实手机扫码和社交平台压缩、低用量用户实际分享反馈、显式纠错界面。

预览采用 HTML、SVG、Canvas 和浏览器原生能力，不新增运行依赖。独立预览的包装器由 Codex 内置 visualize 渲染工具生成，仅用于设计审阅，不作为产品运行模块。
